# QA-Core audit, September 2026

Published 2026-10-04, with a dated erratum of 2026-10-05. Six live runs of the agent against one public demo site, the defects they exposed, the fixes that landed, and what the shipped tests prove. Every number comes from a run-report.json and is reproduced by `npx tsx scripts/audit-metrics.ts`, or is marked "from the run N diagnosis" with the diagnosis file linked. The diagnosis files hold the detail; this report holds the trajectory.

## 1. Summary

Between Sept 15 and Oct 1 the agent ran six times against practicesoftwaretesting.com (the Toolshop) with the same requirements document and the same $6 ceiling. The shipped count went 0, 1, 1, 5, 5, 12 tests; rules covered went 0, 1, 1, 5, 4, 10 of 14; model spend per shipped test (API cost only; the owner's diagnosis and fix time is not counted) fell from no test at $6.08 to $0.51.

Three runs were graded against a bar written before the run. Run 4 met its bar (5 shipped, no rework asking for a missing tool capability). Run 5 missed both lines (5 shipped against 8, 4 rules against 7), and its framework failed 3 of 6 on a clean install after 20 green executions inside the pipeline. Run 6 missed its rework-rate line (62.5 percent against under 50) and met the other three. No missed bar was re-run.

Nineteen fix PRs (#17 to #36, less the docs PR #33) closed the thirty-seven defect rows in section 4, each with a smoke lock. The emitted framework is now executed before the zip is written, which caught one divergence in run 6. Not fixed: the dependency on a shared demo account, pages reached only by an action, a rework rate above the bar, Critic misjudgements (D3), and console contradictions (D8). Three post-run PRs (#34 to #36) are verified offline only.

## 2. Scope and method

One site, practicesoftwaretesting.com, chosen because it is a public demo with a login, a catalogue, a cart, a contact form and registration. One SRS (`toolshop-srs.md`, 14 rules). One ceiling, $6 per run. Six runs from Sept 15 to Oct 1.

What the run folders record about how each run was started (block E of the script output). Runs 2 and 3 came from the dashboard and runs 4 to 6 from the CLI, by `run-meta.json`. Run 1 has no `run-meta.json` (the empty-run path deleted it, fixed in PR #17) and its checkpoint records no surface; the run 1 diagnosis traces it to the gateway. The recorded flags agree on TypeScript, page objects, no feature list, no URL list, replay, three stability iterations, the Stabilizer with three attempts and a $6 ceiling, with two differences: run 1 alone passed `discover: true` (the later runs relied on the SRS to activate discovery), and run 6 alone records `emittedCheck: true`, a flag that exists from PR #30. Run 1's checkpoint carries only five flag keys and no env entry; its $6 ceiling is in its first message event (from the run 1 diagnosis). The SRS: runs 2 and 3 used their own copy, runs 4 to 6 named run 3's copy on the command line, and all five files hash to the same sha256 (`ac278ddf17eb...`), as does the project SRS uploaded on Sept 15. Run 1's copy was deleted with its run-meta and the file its flags name no longer exists, so its hash is not recorded; the run 1 diagnosis (section 8) identifies the project SRS as the document it was copied from.

Before each graded run (4, 5 and 6) a bar was written into STATE.md. After the run it was graded line by line. A missed bar is recorded as missed and the run is never repeated to improve the number.

Every number in the tables below is read from a named key of the run's `run-report.json` by `scripts/audit-metrics.ts` (the surface, flags and SRS hash come from `run-meta.json`, `checkpoint.json` and the SRS copy in the same folder). When a report lacks a field the cell reads "n/r" (not on this report) and the value, where the report needs one, is taken from that run's diagnosis file and marked so. Nothing is computed from a different file. The script also checks its own output against the runs table in STATE.md.

Run 5 is the case that changed the pipeline. Three tests failed on a clean install after 20 green executions (from the run 5 diagnosis) because the emitter keyed page-object fields by intent and 79 calls carried no intent (from the run 5 diagnosis), so a price assertion ran against the page title. Run 6 is the first run where that check ran. The eco-friendly filter test failed it twice with `Expected: < 0 Received: 2` (`emittedFailed[0]`): the emitted spec read the product count before the list rendered, which replay never did because replay waits. The test was dropped before the zip and R3 reads planned-but-dropped. That is D1, fixed in #35 after the run.

Two run 6 tests carry names that claim more than their recordings prove:

- `[edge] clicked a rental product and the detail page showed the same name and price as the listing` was recorded on /category/hand-tools after the Explorer found /rentals empty. Its first step navigates to the hand-tools page. D2, fixed in #34.
- `[negative] rejected login with wrong password and stayed on login page` submits a generated non-existent account: the email fill carries `generate: "email"` and `override: "non-existent-account"`. It proves an unknown-account path, not a wrong password for a known account. D7, open.

Both tests pass. Regenerating an old run from its run-report re-emits the recorded steps and does not rename old tests, so these two names stay in the run 6 zip.

## 7. What the engine does today and what it does not

Does today. Plans from a page snapshot and an SRS, drives a real browser, records steps with role-first selectors, grades every scenario and repairs reworks once, re-runs every survivor four times, emits a page-object framework in TypeScript or JavaScript, runs that framework once before the zip, and accounts for every planned scenario in a balanced funnel. Model spend $0.51 per shipped test on run 6.

Does not yet.

- Shared account dependency. Every login scenario and the auth setup use the site's shared demo account. Runs 2, 5 and 6 each lost the happy login on that account. Run 2's cause is recorded (a lockout from attempts made outside the run); runs 5 and 6 are unexplained. The own-account design (the run registers its own account) is the next PR after this report.
- State-dependent pages. The cart link on this site renders only after an add-to-cart, so no crawl of a fresh session finds it and the cart rules depend on the Explorer reaching the page by action. An action-first discovery rung is a design item.
- Dropped traces. A dropped scenario keeps only its name and verdict on the report; its recorded steps are lost, so a drop cannot be diagnosed from the artifact alone.
- Rework rate. 62.5 percent on run 6 against a bar of under 50. Two of the ten reworks were unjustified (D3); without them the rate is 50 percent, still not under the bar (from the run 6 diagnosis).
- Critic errors (D3). A required success message the site never shows; a rework for a timeout already at the gate floor; cart verdicts that took a badge element count for the badge's value. Documented, not yet fixed.
- Console contradictions (D8). Two rule-coverage totals, a stale first-pass Critic paragraph, the repair budget printed as a ceiling stop, a wrong no-discovered-page warning on saucedemo, and the repair decision line cut by the 240-character cap. Documented, not yet fixed.

## 9. Limits of this audit

- One site and one SRS. The numbers describe the Toolshop and this document, not the agent in general. The five SRS copies that survive hash the same; run 1's copy is lost, so its hash is not recorded. The saucedemo runs are a second, much smaller site.
- A public site that may change between runs. Run 6 saw the site's own footer read `v2.5 | Built 2026-09-30 | Angular 20.0.5` (`console.log` line 327, inside a `wait_for_text` result; `events.jsonl` line 634, the same result at 12:35:05Z). No earlier run's files carry a version or build string, so whether runs 1 to 5 ran against the same build is not recorded.
- A shared demo account, used by anyone who visits the site. Runs 2, 5 and 6 each lost the happy login on it (from their diagnoses). Run 2's cause is recorded (a lockout from attempts made outside the run); runs 5 and 6 are unexplained.
- Clean-install checks run by hand. The run 4, run 5 and run 6 clean-install results come from the owner's machine and are not in any run folder. From run 6 on the pipeline records its own emitted-spec check.
- No run after the post-run fixes. PRs #34 to #36 are verified offline against run 6's artifacts and by their smokes only.

## 10. Open items, ranked

1. Own-account design (run 5 finding 8, run 6 D7): the happy registration's generated account becomes the run's login and duplicate-email seed. It removes the shared account from every login scenario and removes one candidate cause; runs 5 and 6 are unexplained, and it does not claim to fix them.
2. D3, Critic errors: flow evidence from sibling scenarios, no rework for a timeout at the gate floor, a single-element count capture flagged as a presence check. The rework rate cannot pass its bar while unjustified reworks count.
3. State-dependent pages: an action-first discovery rung so the cart feature is planned where the action starts. The cart rules depend on it.
4. D8, console contradictions: one rule-coverage print, the final Critic paragraph from merged verdicts, the repair budget named and rounded, the decision line printed whole. The console is what the owner reads first.
5. Dropped traces kept (redacted) on the report, so a drop can be diagnosed from the artifact.
6. D9 smaller items: RULE 7 exempts headings, rule citations checked against the control the scenario names, cross-page dedup on a stem of the name, the live probe cap on every assertion type, the ceiling checked before the call that would cross it.
7. The run page's recorded count omits the emitted_failed bucket: for run 6 it reads 15 recorded (12 generated plus 3 dropped) where the Explorer recorded 16. Found while writing this report; `scripts/audit-metrics.ts` adds the bucket.
8. reconciliation.dropped must carry the plan's canonical name, never the Critic's echo (standing rule 1).
9. The critique client seam reaches the repair block, so the pass can be driven with a fixture Critic.
10. testid hints recorded as css because the site uses data-test: emit getByTestId with testIdAttribute in the config.
11. Explorer start-up waste: the orientation load of the entry page when the plan names each page.
12. The dashboard's rule table shows not-reachable as not planned.
13. Enumerate every cap, truncation, filter and catch in the pipeline; make each loud or prove it harmless.
14. run-report records its own budgets (step budget, explorer sub-ceiling, repair budget, per-page planner cost).
15. runtime emits discovery events so the live Discovery panel has numbers.
16. Doctrine decision on absence-as-count-zero assertions; SIGINT listener leak in the gateway; CODEBASE.md stale; qa-core-heal 0.3.5 packaging; the smoke suite's four 60 s waits.
