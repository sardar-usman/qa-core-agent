## 3. Engine defects, ranked

### D1. The emitted count capture reads once with no wait; replay waits

Artifact: `tests/cart/cart.spec.ts` in the zip, lines 21, 29 and 40, each `const cap_beforeCartCount = await page.locator("[data-test='cart-quantity']").count();` as the first statement of the test, right after the `beforeEach` goto, with no wait before it. `count()` does not auto-wait. Replay waits: `awaitCaptureReady` in `replay.ts` polls the capture target to at least one match before the read (invariant 39), and the live capture tool did the same during exploration (`events.jsonl`: the `capture` call for "cart badge before add" at 12:36:58 took 5.1 s before its result, and so did the two that followed). The emitted spec is the one place that reads immediately. The eco-friendly filter test is the proof: it captured the product-card count before the list rendered, read 0, and the compare could not hold: `emittedFailed[0].error` is `Expected: < 0 Received: 2`; `emittedRun.tests` records it `failed` with `attempts` 2; it was dropped before the zip (`console.log` line 591) and R3 reads planned-but-dropped (`ruleCoverage.uncovered`). The three cart tests with a `greater` relation passed for a reason that is not the badge: a too-early 0 before the add is less than any count after it, so the compare goes green whether or not the capture read the rendered page (standing rule 2: a failure path that returns a legitimate-looking value). Fix direction: the emitted capture of a count waits the way replay does (poll the locator to at least one match, bounded, before the one-shot read, skipped only for a var that feeds `absent`), emitted by both `pom.ts` and `transcriber.ts`; a smoke that fails on an immediate `count()` after a goto or a click.
