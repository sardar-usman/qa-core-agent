### D1. Discovery stops at a thin sitemap

Artifact: `discovery.json` `method` "sitemap"; `candidates` and `pages` are the same three URLs (/, /contact, /privacy), each `source` "sitemap"; `warnings`: "SRS map present but no feature states a URL; falling through to the next rung.", "robots.txt: 4 Disallow rule(s) apply to our agent; disallowed paths are excluded.", "robots.txt: Sitemap directive found (1)."; events line 7 `discovery: 3 page(s) via sitemap`. Code: `discovery.ts` lines 403 to 407 return from the sitemap rung as soon as it yields one page (`if (sitemapPages.length > 0) { return { ..., method: 'sitemap', ... } }`), so neither crawl rung runs. Run 6 for contrast: its `discovery.json` `warnings` read "sitemap: no usable same-origin pages found; falling through to the crawl." and "crawl: found no additional same-origin pages beyond the entry; falling through.", `method` "browser-crawl", 14 candidates (/, four `/category/*` pages, /rentals, /contact, /auth/login, three `/product/<id>` pages, /privacy, /auth/register, /auth/forgot-password) and 8 planned pages. The site's `sitemap.xml`, fetched after the run (not a run artifact), lists exactly /, /contact and /privacy, with the comment "Product detail pages use dynamic ULID routes served from the API and are intentionally not enumerated here." Run 6 recorded no robots line at all, so the Disallow rules and the Sitemap directive are new since Oct 1.

Consequences in this run: 9 scenarios planned on 3 pages (the per-page cap of 4 bounded / and /contact, events lines 11 and 13; /privacy kept 1 after four page-fit drops, events lines 15 to 19); no category, rentals or product page, so the state probe could only try /, /contact and /privacy (D2) and R6 to R9 read `not-revealed`; the `account` feature had no page (events line 20) and R10 to R12 read `not-reachable`.

Correction to the advisor's reading (the artifact wins). Fixing D1 alone would not have brought back the login page, the registration page or the cart page. The 4 Disallow rules counted in `discovery.json` are, in the `robots.txt` fetched after the run, `/account`, `/admin`, `/auth` and `/checkout`. Both crawl rungs skip a disallowed link before loading it (`discovery.ts` line 648, `if (!robotsAllows(robots, link.pathname)) continue;`, invariant 29), so /auth/login, /auth/register and /auth/forgot-password could not have become candidates on any remote rung. The state probe refuses a revealed path that robots disallows (`state-probe.ts` line 559), and Toolshop's cart page is /checkout (run 6 `events.jsonl` at 12:33:58: "We're on the cart/checkout page with one row." followed by a `toHaveURL` `/checkout`). Also, the run 6 browser crawl did not "find 8 pages": it found 14 candidates and the page filter kept 8. What a D1 fix would bring back on this site: the category, rentals and product pages, so R3 and R5 get their own pages and the probe gets product pages to try (R6's origin side). Line 5 therefore has a second cause: under robots, discovery can only yield the login page when the owner names it, as an SRS-stated URL or in `--urls` (the two rungs that run before robots is fetched, `discovery.ts` lines 374 and 398), and neither the SRS nor the bar's command names one. Whether to point the agent at /auth pages that the site's `robots.txt` now disallows for agents is an owner decision.

Fix direction: with an SRS present, the sitemap rung counts as enough only when its pages carry every requirements feature by page evidence (`pagesCarryingFeature`); otherwise the ladder continues to the crawl and merges both sets, under the same robots rules, caps and delay. The crawl records each link it skipped for robots, and a requirements feature whose only matching paths were skipped says so in the warnings and in rule coverage ("robots.txt disallows /auth"), so a line like bar line 5 can never miss without a stated reason. Lock: a fixture site whose sitemap lists 3 pages and whose crawl finds more.
